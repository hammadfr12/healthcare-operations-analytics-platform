# Data Dictionary

Every table in the analytical store, with its grain and the meaning of each
column.

The store is a single DuckDB file at `data/processed/healthcare_ops.duckdb`,
organised into three schemas:

| Schema | Purpose |
|---|---|
| `core` | Cleaned dimensions and facts, one row per real-world entity |
| `analytics` | Pre-aggregated daily marts, one row per dimension combination |
| `quality` | The audit trail of every pipeline run and what it rejected |

**Grain is stated for every table.** Most errors in operational reporting come
from joining two tables of different grain and double-counting; the grain is
therefore the first thing documented here.

---

## A note on the data

All data is **synthetic and fabricated for demonstration**. No real patient,
staff member, department or facility is represented. It is generated by
`scripts/generate_data.py`, which is fully seeded — the same seed produces
byte-identical CSVs and therefore identical KPIs, which is what makes the
reconciliation figures in `docs/KPI_DICTIONARY.md` checkable.

The pipeline treats this data as if it were sensitive anyway: row-level values
are never written to logs, so the same code path is safe against a real,
de-identified extract.

## `core` — Dimensions and facts

### `core.dim_department` — 8 rows

Grain: one row per department.

| Column | Type | Notes |
|---|---|---|
| `department_id` | VARCHAR | Primary key. `DEPT-01` … |
| `department_name` | VARCHAR | Display name, e.g. `Emergency` |
| `specialty_group` | VARCHAR | Coarser grouping for comparison, e.g. `Emergency & Acute` |

### `core.dim_facility` — 2 rows

Grain: one row per facility.

| Column | Type | Notes |
|---|---|---|
| `facility_id` | VARCHAR | Primary key. `FAC-01`, `FAC-02` |
| `facility_name` | VARCHAR | Display name |

### `core.dim_date` — 365 rows

Grain: one row per calendar day. The date spine.

| Column | Type | Notes |
|---|---|---|
| `date_day` | DATE | Primary key |
| `date_week` | TIMESTAMP | Week-start bucket |
| `date_month` | TIMESTAMP | Month-start bucket |
| `year_number`, `month_number`, `day_of_month` | INTEGER | Calendar parts |
| `day_of_week` | INTEGER | ISO: 1 = Monday |
| `is_weekend` | BOOLEAN | |

Trend charts LEFT JOIN this spine, so a day with no activity appears as an
explicit zero rather than vanishing from the chart and silently compressing the
time axis.

### `core.fct_appointments` — 76,839 rows

Grain: **one row per appointment** (one booking). The appointment fact.

| Column | Type | Notes |
|---|---|---|
| `appointment_id` | VARCHAR | Primary key. `APT-0000002` … |
| `facility_id`, `department_id` | VARCHAR | Foreign keys to the dimensions |
| `visit_type` | VARCHAR | `new`, `follow_up`, `urgent`, `procedure` |
| `appointment_status` | VARCHAR | `completed`, `cancelled`, `no_show`, `scheduled` |
| `cancellation_reason_category` | VARCHAR | Populated only when cancelled; see below |
| `appointment_created_at` | TIMESTAMP | When the booking was made (UTC) |
| `scheduled_start_at` | TIMESTAMP | When the appointment is scheduled for (UTC) |
| `appointment_date` | DATE | Date basis for this fact — **not** `metric_date` |
| `is_terminal` | BOOLEAN | `completed` + `cancelled` + `no_show` |
| `is_completed`, `is_cancelled`, `is_no_show`, `is_open` | BOOLEAN | Mutually exclusive state flags |
| `lead_time_days` | DOUBLE | `scheduled_start_at − appointment_created_at` |
| `lead_time_is_valid` | BOOLEAN | False when the created-at timestamp is missing |

> **Note the date column.** This fact table dates on `appointment_date`. The
> daily marts date on `metric_date`. Filter predicates for this table must come
> from `FilterSet.fact_appointment_predicates()`, not the mart builder — using
> the wrong one is a binder error, not a silent wrong answer.

**Cancellation reason categories**, by who initiated:

| Initiator | Categories |
|---|---|
| Patient | `patient_unavailable`, `patient_rescheduled`, `transport` |
| Provider | `provider_unavailable`, `schedule_change` |
| Facility | `facility_closure`, `equipment_unavailable` |

### `core.fct_encounters` — 78,142 rows

Grain: **one row per encounter** — a patient actually seen. The patient-flow
fact.

| Column | Type | Notes |
|---|---|---|
| `encounter_id` | VARCHAR | Primary key. `ENC-0000001` … |
| `appointment_id` | VARCHAR | Foreign key; **null for walk-ins** |
| `facility_id`, `department_id` | VARCHAR | Foreign keys to the dimensions |
| `encounter_status` | VARCHAR | e.g. `completed` |
| `visit_type`, `appointment_status` | VARCHAR | Carried from the appointment where one exists |
| `is_walk_in` | BOOLEAN | True when there was no appointment |
| `check_in_at`, `service_start_at`, `service_end_at` | TIMESTAMP | The flow timestamps (UTC) |
| `encounter_date` | DATE | Date basis for this fact |
| `is_completed_visit` | BOOLEAN | |
| `wait_minutes` | DOUBLE | `service_start_at − check_in_at` |
| `wait_invalid_reason` | VARCHAR | Why a wait was excluded, when it was |
| `visit_duration_minutes` | DOUBLE | `service_end_at − service_start_at` |
| `is_duration_outlier` | BOOLEAN | True when > 4 hours |

> **Encounter count ≠ appointment count.** Walk-ins have an encounter and no
> appointment, and not every appointment produces an encounter. The two facts
> are never joined to produce a single "visits" number, because that number
> would not mean anything.

**Wait exclusion rules.** A wait is invalid when it is negative (service began
before check-in) or implausibly long (>24 hours). Invalid waits are excluded
from wait statistics but remain in the table with `wait_invalid_reason`
populated, so the exclusion is auditable.

### `core.capacity_daily` — 2,920 rows

Grain: one row per **department per facility per day**.

| Column | Type | Notes |
|---|---|---|
| `metric_date` | DATE | |
| `facility_id`, `department_id` | VARCHAR | |
| `available_slots` | INTEGER | Slots the department could have offered |
| `staffed_slots` | INTEGER | Slots actually staffed |
| `occupied_slots` | INTEGER | Slots used |
| `utilisation_rate` | DOUBLE | `occupied_slots / available_slots` for this day |

This table is **optional input**. When it is absent, capacity utilisation is
reported as unavailable rather than as zero — see the KPI dictionary.

## `analytics` — Daily marts

Marts are pre-aggregated so the dashboard does not scan fact tables on every
request. Each mart keeps its dimension columns, so the same
`FilterSet` predicates apply to a mart and to the facts it came from.

### `analytics.mart_appointments_daily` — 19,447 rows

Grain: one row per **day × facility × department × visit type × status**.

| Column | Type | Notes |
|---|---|---|
| `metric_date` | DATE | |
| `facility_id`, `department_id`, `visit_type`, `appointment_status` | VARCHAR | The grain dimensions |
| `appointment_count` | BIGINT | Appointments in this cell |
| `terminal_count` | BIGINT | Of which terminal |
| `completed_count`, `cancelled_count`, `no_show_count`, `open_count` | BIGINT | State breakdown |
| `lead_time_valid_count` | BIGINT | Appointments with a usable created-at |
| `lead_time_sum_days` | DOUBLE | Sum, so lead time is recomputed not averaged |

### `analytics.mart_encounters_daily` — 17,180 rows

Grain: one row per **day × facility × department × visit type × appointment
status × encounter status**.

| Column | Type | Notes |
|---|---|---|
| `metric_date` | DATE | |
| `facility_id`, `department_id`, `visit_type` | VARCHAR | |
| `appointment_status`, `encounter_status` | VARCHAR | |
| `encounter_count` | BIGINT | |
| `completed_visit_count` | BIGINT | |
| `walk_in_count` | BIGINT | Encounters with no appointment |
| `wait_valid_count` | BIGINT | The denominator for mean wait |
| `wait_sum_minutes` | DOUBLE | Numerator for mean wait |
| `wait_invalid_count`, `wait_negative_count`, `wait_implausible_count` | BIGINT | Exclusion audit |
| `duration_valid_count` | BIGINT | |
| `duration_sum_minutes` | DOUBLE | |
| `duration_outlier_count` | BIGINT | Visits over 4 hours |

Sum-and-count rather than stored averages: averaging daily rates would weight a
quiet Sunday equally with a busy Monday.

### `analytics.mart_capacity_daily` — 2,920 rows

Grain: one row per **day × facility × department**.

| Column | Type | Notes |
|---|---|---|
| `metric_date` | DATE | |
| `facility_id`, `department_id` | VARCHAR | |
| `day_count` | BIGINT | Days contributing to this cell |
| `available_slots`, `staffed_slots`, `occupied_slots` | HUGEINT | Totals |
| `utilisation_valid_days` | BIGINT | Days with usable capacity data |
| `occupied_slots_valid`, `available_slots_valid` | HUGEINT | Totals **over those days only** |

The `_valid` columns are the ones utilisation is computed from. Days with
missing capacity data are excluded from both sides of the ratio; including them
on one side only would bias the figure.

### `analytics.mart_flow_distribution_daily` — 34,665 rows

Grain: one row per **day × facility × department × visit type × wait bucket**.

| Column | Type | Notes |
|---|---|---|
| `metric_date` | DATE | |
| `facility_id`, `department_id`, `visit_type` | VARCHAR | |
| `wait_bucket_lower_minutes` | INTEGER | Bucket start |
| `wait_bucket_label` | VARCHAR | Display label |
| `encounter_count` | BIGINT | Encounters in this bucket |
| `wait_sum_minutes` | DOUBLE | Sum of waits in this bucket |

Buckets are 15 minutes wide. This is the only mart where `encounter_count`
summed across rows still equals the encounter total — the bucket dimension is
additive, unlike the status dimensions elsewhere.

## `quality` — The audit trail

### `quality.data_quality_runs`

Grain: one row per pipeline run.

| Column | Type | Notes |
|---|---|---|
| `run_id` | VARCHAR | |
| `started_at`, `completed_at` | TIMESTAMP | |
| `status` | VARCHAR | `succeeded` or `failed` |
| `input_rows`, `accepted_rows`, `rejected_rows` | BIGINT | |
| `error_summary` | VARCHAR | Populated on failure |

### `quality.data_quality_issues`

Grain: one row per check per run.

| Column | Type | Notes |
|---|---|---|
| `run_id` | VARCHAR | |
| `check_id` | VARCHAR | e.g. `appointments.appointment_id.duplicate` |
| `category` | VARCHAR | See below |
| `severity` | VARCHAR | `error` or `warning` |
| `table_name`, `column_name` | VARCHAR | Where the problem was found |
| `row_count` | BIGINT | How many rows were affected |
| `message`, `remediation` | VARCHAR | What is wrong, and what to do |
| `sample_keys` | VARCHAR | A few offending keys, for locating the rows |

**Severity decides what happens.** An `error` fails the row (it is quarantined);
a `warning` is reported and the run continues. The pipeline degrades visibly
rather than going dark.

**Issue categories:**

| Category | Raised when |
|---|---|
| `schema` | Expected columns are missing |
| `missing_value` | A required column is null |
| `duplicate_key` | A primary key or declared grain repeats |
| `malformed_timestamp` | A timestamp cannot be parsed |
| `invalid_status` | A status value is outside its allowed set |
| `invalid_value` | A value is outside its allowed range |
| `invalid_type` | A value cannot be cast to its expected type |
| `referential_integrity` | A foreign key has no matching dimension row |
| `invalid_duration` | A duration is negative or implausible |
| `consistency` | Values are individually valid but contradict each other |

## Regenerating

```bash
make data        # regenerate data/raw/*.csv from the seeded generator
make pipeline    # rebuild the store from data/raw
```

`make reset` deletes the store; the next `make pipeline` rebuilds it from
scratch. `data/raw/flawed/` holds a deliberately corrupted fixture so the
validation layer can be demonstrated failing without touching the happy path.
